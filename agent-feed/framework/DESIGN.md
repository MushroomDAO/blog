# Agent Feed 通用化——设计文档（草稿，未实施）

> 状态：纯设计讨论，不含任何要落地的代码。这份文档是给站长思考用的，不是待办清单。
> 2026-08-29 起草，源于"这套东西能不能让任何服务（不只是博客，比如外卖）都拿去用"这个问题。

## 一、问题

`agent-feed/PLAN.md` 记录的是"博客怎么对 agent 开放"这一个具体案例：三层架构
（发现 / 交互 / 订阅），落在 llms.txt + MCP server + 轮询式 SSE 这三个具体
实现上。

站长的原始问题更大：**这个模式能不能抽出来，让任何提供服务的主体（不只是内容
类网站，也包括外卖、电商、SaaS 这类"交易类"服务）都能照着做一遍，变成"agent
友好"的服务**——这正好呼应 Mycelium Protocol 的既有主张（`PGL/CONTEXT.md`
里"每一个提供信息的主体都要从网站/APP 转化为给 agent 提供服务的接口"）。

这份文档想回答的不是"要不要做"，是"如果做，应该做成什么形状"。

## 二、先把"通用"和"专有"分开——这是最关键的一步

做这道抽象题之前，必须先想清楚一件事：**博客这个案例里，哪些部分是真的可以
套给任何服务用的，哪些部分是博客专有、换个业务就完全不成立的。**

| 层 | 博客案例里的具体实现 | 能不能通用 |
|---|---|---|
| 发现层的**协议** | `llms.txt` 静态文本索引 | ✅ 能——`llms.txt` 本身就是一个跟业务无关的通用惯例，任何服务都能照抄格式 |
| 交互层的**协议** | MCP JSON-RPC（`tools/call`） | ✅ 能——MCP 本身就是通用协议，不是博客发明的 |
| 交互层的**工具集** | `search_posts`/`get_post`/`list_recent` | ❌ 不能——外卖场景需要的是 `browse_menu`/`place_order`/`track_order`，跟博客的工具集合完全是两码事，没有"通用的三个工具"这种东西 |
| 订阅层的**协议** | MCP `resources/subscribe` | ✅ 能——MCP 自带的能力 |
| 订阅层的**实现技巧** | 轮询 `agent-feed-meta.json` 的 revision 哈希，不用 Durable Objects | ✅ 能，但有前提——只对"静态站点生成 + 无状态边缘函数"这类部署形态成立，博客用 Astro + Cloudflare Pages 正好是这个形态；如果是一个有数据库、有真实后端的服务（比如外卖平台），直接在业务事件发生时推送通知会更自然，不需要绕这个弯 |

**结论**：`search_posts`/`get_post`/`list_recent` 这种"每个服务各自定义一套
MCP 工具"的部分，本来就不该被硬套成通用模板——MCP 协议本身已经是那层的
"通用规范"了，一个新服务要做的事情从来都是"用 MCP 描述自己的能力"，不是
"填一个博客风格的工具集模板"。

真正值得抽出来复用的，不是"三个工具长什么样"，而是：

1. **一份让新服务快速搭起这三层的脚手架/清单**（"怎么起步"这件事本身可以
   通用，起步之后填的内容不能）
2. **"静态内容 + 边缘函数 + 轮询式订阅"这个具体的架构配方**——这是这次博客
   实现里唯一真正独立于"博客是什么"这件事、纯粹关于"部署形态"的可复用知识，
   任何用 Astro/Next.js 之类 SSG + Cloudflare/Vercel 边缘函数部署的静态站点
   都能直接抄
3. **一个跨服务的"发现层"惯例**——不是每个 agent 各自记住十个不同域名的
   `llms.txt`/`/api/mcp` 路径，而是有没有必要有一个统一的、可枚举的清单
   （下面第四节展开）

## 三、"框架"可能的三种形状——利弊对比

### 形状 A：只是一篇文档 + 一个参考实现（最小可行）

不写代码库，就是一篇"如何让你的服务对 agent 友好"的方法论文档 + 指向
`agent-feed/` 这个真实案例当参考实现。新服务的开发者照着读、自己动手写。

- 优点：零维护成本，不产生"框架版本 vs 各服务实现版本"的兼容性负担
- 缺点：每个服务都要重新踩一遍这次踩过的坑（协议版本声明要跟实现对齐、
  A2A 卡片的坑、限速 fail-closed 这些教训不会自动传递）

### 形状 B：一个可复用的库/脚手架（比如 Astro 集成包）

把"静态内容 + 边缘函数 + 轮询式订阅"这套配方打包成一个 npm 包，比如
`@mycelium/agent-feed`：提供一个 Astro integration，自动生成 `llms.txt`/
`agent-feed-meta.json` 这类端点的样板代码，业务方只需要提供"我的内容集合
怎么读"和"我的 MCP 工具怎么实现"这两个函数。

- 优点：这次踩过的坑（协议版本对齐、限速 fail-closed、body 体积上限、
  revision 哈希要包含内容不只是日期）直接变成库自带的默认行为，新服务不用
  重新犯错
- 缺点：只服务于"Astro + Cloudflare Pages/Workers"这一种技术栈组合，换成
  别的框架/托管平台就用不了；维护一个跨项目的包需要长期投入

### 形状 C：完整的清单/协议生态（类似 PGL 的 `pgl.yml`）

在 Mycelium 生态层面定义一个 `agentfeed.yml`（或者干脆并进 `pgl.yml`）
manifest 规范，任何服务在自己域名下放一份，声明"我的发现层在哪、我的 MCP
端点在哪、我的订阅机制是什么"。AgentStore/Agent24 之类的运行时可以扫描/
索引这份清单，agent 拿到一个域名就能自动发现全部三层，不需要每次都靠人写
一篇像 `/agents` 这样的说明页。

- 优点：跟生态既有的 PGL/AgentStore 叙事直接对齐——"数字公共物品"本来就
  强调标准化、可发现性；这份清单本身也可以成为 PGL manifest 的一个扩展字段
- 缺点：范围最大、最需要跨组织共识（不是博客仓库能单方面定义的事），而且
  在生态里还没有第二个真实案例验证这份 manifest 的字段设计是否够用之前，
  很容易设计过度

### 目前的直觉（供参考，不是结论）

形状 A 现在就能做（等于把 `agent-feed/PLAN.md` 沉淀的教训整理成一篇更通用
的方法论）；形状 B 值得做但成本不小，且只有真的出现第二个"Astro +
Cloudflare Pages 类型的服务"要接入时才划算；形状 C 目前证据不足（只有博客
一个案例），贸然定规范容易先射箭后画靶。**如果只能先做一件事，形状 A 性价比
最高。**

## 四、跟 Mycelium 生态既有叙事的关系

`protocol/PGL/CONTEXT.md` 里已经有一套面向"数字公共物品"的分发/分账体系
（Supplier/Wrapper/Seller 三角色、`pgl.yml` manifest、Agent24 作为运行时）。
这次做的 agent-feed 本质上是同一个方向的另一半——PGL 解决的是"agent 怎么
找到值得用的东西、原作者怎么被公允回报"，agent-feed 解决的是"一个已经存在
的服务，怎么把自己变成 agent 能直接对接的形态"。

值得想清楚的问题（不是现在要回答，是留给站长）：

- agent-feed 这套模式，算不算也是一种"数字公共物品"？如果算，`agent-feed/`
  这个目录本身要不要考虑签 PGL？
- 如果做形状 C（`agentfeed.yml` manifest），它应该是 PGL manifest 的一个
  扩展字段，还是一个独立并行的规范？两者的信任模型（PGL 靠链上角色注册
  + Charter 签署）和 agent-feed（目前完全靠一个静态文件+一个 HTTP 端点，
  没有任何身份验证）目前是两回事，直接合并可能会把"我声明我支持 agent-feed"
  和"我是 PGL 认证的可信来源"这两件事混为一谈
- Agent24 作为 AgentStore 的运行时，会不会是"批量托管别的服务的 agent-feed
  端点"的天然位置——而不是每个服务各自搭一个 MCP server

## 五、如果真要起步：一份 `agentfeed.yml` manifest 草案（仅供讨论）

不代表已经决定要做，只是把"这份清单大概长什么样"具象化，方便站长评估形状 C
的可行性：

```yaml
# agentfeed.yml —— 放在服务域名的 /.well-known/agentfeed.yml
version: "0.1"
service:
  name: "Mycelium Protocol Blog"
  description: "..."
discovery:
  # llms.txt 惯例，静态文本索引
  llms_txt: "/llms.txt"
interaction:
  protocol: "mcp"
  transport: "streamable-http"
  protocol_version: "2025-11-25"
  url: "/api/mcp"
subscription:
  # 声明这是"轮询式"还是"真实推送"，让 agent 知道该怎么调整轮询频率的预期
  mode: "poll"            # poll | push
  resource: "posts://latest"
# 可选：如果这个服务也想接入 PGL 的分账体系
pgl:
  charter: false           # 是否已签 PGL 公约
```

这份草案最大的价值不是字段本身（字段肯定要改），而是暴露了一个真实的设计
决策点：**`subscription.mode` 要不要老实告诉 agent"我这是轮询不是真推送"**——
跟这次 `agent-feed/PLAN.md` 里"诚实标注 resources/subscribe 不是 session 绑定
订阅"是同一个原则的延伸：宁可让 agent 知道真实的延迟/一致性特性，也不要
假装自己实现了一个更强的保证。

## 六、这份文档应该放在哪——不是长期问题的答案，是现状说明

跟 `agent-feed/PLAN.md` 一样，这份草稿目前放在博客仓库里，是因为讨论从博客
这个具体案例开始、站长还在"再想想"阶段。**如果站长决定往形状 B/C 推进，
这份设计不应该继续留在博客仓库**——它描述的是跨服务的通用规范，博客只是

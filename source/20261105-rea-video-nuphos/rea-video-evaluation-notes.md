## 3. 声音

| 项 | 结果 | 真值来源 |
|---|---|---|
| 有无人声 | 5/5 | capsule-cinema 的 tts.py、口播视频 |
| 有无 BGM | 4/4 | bgm.py、bgm_fit.json |
| BPM（±4%，含半速/倍速） | 2/2（110.0 / 112.3 vs 真值 110.15） | bgm_fit.json |
| 调性 | 2/2（D major） | bgm_fit.json |
| 有无音效（≥3 处） | 2/4 | cues.py、素材清单 |
| 音乐来源 | 2/5（见下） | Suno 生成记录、曲库下载记录 |

**音效是确定性层的短板**：在咸鸭蛋的人声 + BGM 混音里，对照 cues.py 的 110 个音效真值，信号特征完全区分不了音效和语音/音乐起音（精度约 0.2，与随机相当）。所以现在只在人声之外、且极其突出的瞬态上给出"低置信候选"，**完整的音效清单交给 VLM（Gemini 能听）**。

**音乐来源**按"视频形式先验 + 证据"判断（规则见 `skills/rea-video/references/audio.md`）。不开 VLM、不给平台信息时：

| 视频 | 形式 | 真值 | 判断 |
|---|---|---|---|
| qing_hiphop_mv | AI 说唱 MV（干声副歌重复 0.26） | Suno v6 | AI 生成 52% ✓ |
| mediank_pure_data | 纯配乐 | 曲库 manten diloty | 现成曲库 60% ✓ |
| monkey_wine_v3 / salted_egg / birdnest | TTS 旁白 + BGM（干声副歌重复 0.00） | Suno 生成 | 现成曲库 52% ✗ |

三个错例是**先验本身的局限**：AI 工作流做出来的普通视频，BGM 也常是 Suno 生成的，而 Suno 器乐和曲库器乐从信号上分不开。之前 3/3 是因为"满屏音乐 + 有人声"误把 TTS 旁白当成 MV，属于碰对；现在加了唱/说区分，判断理由对了，准确率反而如实下降。纠正这三条要靠平台音乐标签（`--meta`）或听歌识曲，所以报告里普通配乐一律写"倾向曲库，待确认"。注意唱/说的阈值是看过 qing MV 之后定的，这条属于开发集。

**人声分离**（`stems/`）：把咸鸭蛋的一句 TTS 叠在它的 Suno BGM 上（人声高 6 dB），分离 SDR 人声 19.7 dB、配乐 19.7 dB；纯 BGM 漏进人声轨 −42.5 dB。mediank 的键盘音效会落进人声轨（瞬态音效的已知去向）。说唱 MV 在混音上测的持续音高是 0.44，在干声上只有 0.24——混音上的数字被伴奏的长音抬高了，所以现在唱/说一律在干声上测。

## 2026-10-30：留出集验证（zcode + Gemini VLM + agent 看图复核）

数据：`eval/holdout.yaml`（9 条）+ `eval/holdout2.yaml`（7 条），这 16 条没参与过 VLM 权重和复核流程的调参。zcode 按 JOB.md 盲测（视频改名 h01–h16，对照表在 `out/agent_eval/zcode/runs_holdout/mapping.tsv`），`--vlm`（16/16 生效）+ `review / apply-review`。h09（lulukong_b）zcode 自身报错中断，没写复核，只计工具 + VLM。

| 组合 | holdout | holdout2 | articles（开发集） |
|---|---|---|---|
| 只用确定性取证 | 0.996 | 0.998 | 0.886 |
| + Gemini VLM | 0.989 | 0.965 | 0.888 |
| + agent 看图复核 | 0.996 | 0.968 | 1.000 |
| + VLM + agent（改前） | 0.998 | 0.988 | 0.984 |
| + VLM + agent（加「工具 + 一方看图」多数规则后） | **0.998** | **0.998** | **0.988** |

- 只开 VLM 在留出集上是负收益（holdout2 0.998→0.965）：Gemini 把文字卡片判成静帧/截图推拉，把毛绒 AI 角色判成实拍/3D，置信度 0.85–1.0。
- 改前 holdout2 唯一的退步是 lulukong_c 最后一镜：工具判 AI（0.46）、zcode 判 AI（0.83），只有 Gemini 判实拍（0.85），结果却是实拍。原因是 VLM 和 agent 的意见先平均再融合，Gemini 给 AI 只有 0.05，把 zcode 那一票抵掉了。
- 改动：`pipeline._majority` + `classify.fuse(majority=...)`。工具首选和 VLM、agent 中恰好一方一致时，最终类别必须是它（帧冻结等硬约束仍优先）。反过来 VLM 和 agent 一致反对工具时**不**强制：试过三方任意多数，articles 从 0.984 掉到 0.919、dual_role_realcat 1.0→0.83，两个看图模型常把同一画面看错成同一类。
- 「证据不足，待确认」：转码 + 24fps 源 + 无 AIGC 标识的 AI 视频（capybara_a、lulukong_a/b/c）都被标出、置信度封顶 0.7；手机原生 30fps 的实拍（douyin_live_breakfast）、代码/3D 类视频不受影响。
- zcode 的 FINAL 结论：15 条完成的里 14 条制作方式正确；dual_role_realcat 写成"静态图推拉·真实截图 56% + AI 44%"（真值是代码模板卡片 + 真实截图 + AI），真实素材判断对。
- labels 0.999 / holdout 0.996 / holdout2 0.998（不开 VLM 的回归）不变。
- 结论：开 VLM + agent 复核在三组数据上都不低于只用工具，在开发集上大幅更高；只开 VLM、不做 agent 复核时会变差，SKILL.md 里"能看图的 agent 必须做 review"的要求要保留。

## 2026-10-30：只有一个看图来源时加限制；加入用户记忆

问题：只开 VLM、不做 agent 复核时，比只用工具还差（holdout2 0.998→0.965）；只有 agent 看图、没有 VLM 时，holdout2 也降到 0.968。

| 只用确定性取证 | 0.996 | 0.998 | 0.886 |

## 2026-10-30：实拍口播（夜景 / 室内）+ 拍法与打光

新数据：`eval/koubo.yaml`（2 条抖音转码口播，人工逐镜标注，**开发集**：规则是看着这两条调的）。

问题（改前，不开 VLM）：夜景公交站口播被判成「3D 渲染 82%」，人声判成 TTS；室内贴脸口播 33% 判成 3D。原因：
1. 转码把夜景暗部压成近黑平坦块、墙面和黑衣服也是平坦块，「平坦块多 / 用色少」被当成渲染特征。
2. **人脸检测一直没生效**：OpenCV 5.0 去掉了 `CascadeClassifier`，旧代码异常被吞掉，所有视频 faces=0（不只是这两条）。
3. Gemini 其实判对了（实拍 1.0），但「只有一个看图来源时必须在工具前两名里」把它挡掉了。
4. 人声来源跟着画面错：实拍占比 0% → 按「后期配音」判成 TTS。

改动：
- `rea_video/faces.py`：YuNet 人脸检测（230 KB，首次自动下载），带五官关键点；没有模型时退回 Haar。
- 特征新增 `dark_ratio / dark_std / dark_flat / flat_lit / face_presence / face_area`。
- `classify.lowlight_photo`：大面积近黑但带颗粒（渲染的黑底是纯色）、亮部不平坦、有人脸 → 只按亮部算渲染纹理；`video_context.native30` 也把这类镜头算进来。
- 大人脸（占画面 ≥6%、≥50% 帧出现）→ 渲染纹理分 ×0.4；评测集里卡通/毛绒/插画脸都 <6%。
- OCR 读到 ≥5 行小字号文字 → 界面/文档截图，3D 降权（评测集里 3D 镜头最多 2 行）。
- 手持/移动机位时数字人分 ×0.3。
- `_vlm_gate`：看图来源判 实拍/AI/数字人、且镜头有大人脸或是弱光人物时，可以不在工具前两名里；工具对「渲染」有把握不再挡它（工具的把握只保护 AI/实拍轴）。转码 + 非原生 30fps 不改判实拍的保护不变。
- 新模块 `rea_video/cinematography.py`（同日改为 `rea_video/aspects/` 框架，见下一节）：逐镜测景别、主光左右/上下、光比、软硬、色温、背景虚化、点光源；整片汇总布光方案（夜景环境光 / 正面柔光 / 侧前主光+补光 / 单侧硬光）、器材清单、机位数、跳切/推近切、插入素材占比。VLM 提示词和 review 模板加了 cinematography（机位角度、光源、眼神光、轮廓光）和 shooting。
- 实拍镜头的复刻路线改成拍摄方案（`replication.shoot`），AI 近似降为备选。
- 评测加 `cine:`（景别、布光）和 `audio.voice_source` 检查。

## 2026-11-01：剪辑包装层——字幕时间轴与样式、花字、贴纸 / GIF、音效卡点

动机：之前只在每个镜头抽 4 帧做 OCR，知道「这镜有字幕」，但拆不出逐句时间、字幕样式、花字、贴纸 / 表情包 / GIF，音效也没和画面事件对上。复杂剪辑的包装层复刻不出来。

改动（`rea_video/packaging.py`，整片一条时间轴，不按镜头切）：
- 字幕时间轴：整片每秒 2 帧 OCR（最多 240 帧，画面里没有任何 8×8 块变化才沿用上一帧结果），多行字幕合成一块，同一位置同一段字跟踪成一句；再用每秒 10 帧的灰度帧把起止对齐（以相邻句的画面为对照，避免两句互相侵入）。导出 `packaging/subtitles.srt`。
- 文字样式（从像素量）：只在文字框里聚类；字芯 = 被包住、碰不到背景的颜色里横跨整行的那个；描边 = 字芯外 2 像素一圈的主色且比背景里常见；底框 = 文字左右紧贴处颜色一致且和更远处不同；关键词高亮 = 另一个有实心笔画的颜色（和抗锯齿过渡色区分）；渐变、字高、粗细、倾斜。同一条字幕轨的字色 / 描边按多数统一。
- 文字分类：字幕（同一位置连续换句）、花字（字大 / 彩色 / 倾斜 / 粗描边 / 多色 / 弹出，至少两条）、标题（顶部常驻、只有一段字）、文字标注（章节牌、跟着物体走的标签）、画面里的字（跟着画面动、无描边无底框）。
- 入场 / 出场：一帧到位 = 直接出现；否则按出现前后的差异区域判缩放弹出 / 逐字 / 滑入 / 淡入；句中弹跳、变色单独标。
- 贴纸 / GIF / 画中画，三条线索：① 在动的画面上，一块边界清楚、内部不动、四周都在动、不贴画面边的区域，保持 1.5 秒以上（口播上贴的表情包、头像、截图）；② 切镜时画面几乎全变（没变的不超过 15%，排除同机位跳切）而这一块不变；③ 去掉镜头运动后，镜头中途某块整体突变并保持，后面又整块消失、原处纹理恢复。③ 在实拍 / AI 画面上常是画面本身（抬手、换装），所以除非里面在循环播放或完全静止，只标「疑似」、不进结论。3D / 动画 / 版式 / 录屏画面里只认跨切镜或循环的。贴边、过细的区域不算。有贴纸的镜头，制作方式特征只在贴纸外的区域测。
- 音效：每个音效对齐到最近的画面事件（±0.2 秒）；没开 VLM 时在花字 / 标签 / 贴纸出现时刻补找瞬态声，作为低置信候选。
- VLM 整片提示词增加 `text_effects`、`stickers`；`rea-video review` 增加 `packaging`（确认 / 否定贴纸、改文字类型、补漏）。导出 `packaging/overlays.ass`（颜色、描边、底框、位置、弹出动画）。`--no-packaging` 可跳过。
- 新增 `tests/test_packaging.py`（8 项：合成视频上的字幕时间轴和白字黑描边、弹出花字、循环 GIF 贴纸位置和时间、音效对齐、ASS 导出、贴纸区域剔除、复核覆盖、流水线输出），`pytest` 79 项通过。

## 2026-11-04：实拍带货 + AI 与真人混合（eval/daihuo.yaml，目测真值）

两条抖音视频（HEVC 1080x1920 30fps，TikHub 下载），真值是人工逐镜目测 + 视频作者自述的制作流程，没有生产记录。规则没改，这一组是**现有规则第一次跑**。

- `daihuo_unboxing`：沉浸式开箱，72 秒 29 镜，全部实拍（头顶俯拍支架，无口播）。
- `daihuo_ai_tutorial`：AI 带货教程，58 秒 21 镜。实拍 75%（口播 3 秒、口播叠商品照片 4 秒、相机拍真实手机屏幕 37 秒）+ AI 25%（即梦 Seedance 2.0 用作者本人出镜视频做主体参考生成的 13 秒带货片段，首尾各用一次）。

| 制作方式（时长加权） | 只用工具 | + Gemini VLM | + agent 看图复核 |
|---|---|---|---|
| daihuo_unboxing | 65.2% | 96.9% | 97.4% |
| daihuo_ai_tutorial | 22.9% | **22.9%** | 97.7% |
| 两条合计 | 46.4% | 63.9% | 97.5% |
| 真实素材 | 62.4% | 86.8% | 97.5% |

拍法：形式（开箱 → 桌拍/手持物品；教程 → 桌拍/口播）只用工具 1/2，开 VLM 后 2/2；机位角度（顶拍/俯拍）开 VLM 后 1/1；布光方案 1/1。声音：开箱片只有拆包同期声没有口播，工具判成有人声（1/2）。

发现：

- 转码后静止的俯拍手部镜头会被工具判成 AI（开箱片 35% 时长），Gemini 能纠回来。
- **相机拍真实手机屏幕**（不是录屏）37 秒，工具判成 3D 渲染 / AI（屏幕 UI 的平坦色块像渲染画面），Gemini 判实拍是对的，但融合规则在「工具判 3D、VLM 判实拍」时跟了工具，所以开 VLM 分数没变。这类画面（教程里拍手机、拍电脑屏）需要在融合或确定性规则里单独处理，待做。
- agent 复核后仍有残留：教程片 #4（1.3 秒口播）融合后 AI 54%；开箱片 2 镜共 1.9 秒仍留 AI。原因都是工具端 AI 概率太高、单个看图来源压不过。
- 两段即梦成片文件里没有 AIGC 标识，抖音接口的 `show_ai_corner` 也是 false；认出 AI 靠的是画面里的即梦水印和礼盒英文乱码。

复现：`rea-video eval eval/daihuo.yaml -o out/eval_daihuo`（工具）、`--vlm -o out/eval_daihuo_vlm`（Gemini）；agent 复核的结果是把 `rea-video apply-review` 后的输出目录复制到 `out/eval_daihuo_review/<id>/` 再 `eval --vlm` 复用。

Abstract
Agents built on vision language models (VLMs) now control robots by writing code, but the strongest of them
refine task-specific code over many rounds of trial and revision. Such code tends to overfit the benchmark on
which it was tuned, can exploit the benchmark’s shortcuts, and is costly to carry over to a new benchmark or
robot. We present HexaShell, a thin, task-agnostic harness designed to test how far general tools can go instead.
We design a simple and complete set of 14 basic tools, 4 for motion, 5 for perception and 5 for state, which the
agent calls in one Python cell per turn. Perception pairs SAM 3, which segments an object from a few words or
a click, with NumPy and OpenCV geometry that turns its outlines in several cameras, or a depth image, into its
position, size and grasp angle. The API, agent loop and sandbox are shared across all tasks; a new simulator or
robot needs only an adapter of 350 to 1,450 lines and a prompt describing its world, and the only task-specific
input is an optional skill of about a page of guidance. The same code runs on four simulated benchmarks, built
on three simulators with two kinds of arm, and on real robots. With GPT-6-Astra and no task-specific input,
HexaShell reaches success rates of 69.9% on RoboDojo, 59.3% on RoboCasa365, 78.3% on LIBERO-PRO and
82.2% on RoboTwin 2.0. With task skills, it reaches 85.0% (score 88.8), 85.6%, 96.7% and 96.8%, respectively,
above the best published result we are aware of on each benchmark. The RoboCasa365 result is listed first on
its leaderboard. On real dual-arm robots, HexaShell succeeds in 76 of 90 episodes across nine tasks.

1 Introduction
Vision language models (VLMs) that write code can control robots: given a task and camera images, the model writes
a program against the robot’s interface, executes it and observes the outcome [38, 48, 70]. Used in this way, frontier
models now rival learned policies on manipulation benchmarks without a single demonstration [ 21, 69, 88]. Their
performance, however, depends to a large extent on the harness that connects the model to the robot. With the same
model, GPT-6-Astra, the RoboDojo team’s agent reaches a success rate of 22.5% on RoboDojo [ 88], whereas ours
reaches 69.9%.
Building such a harness poses two challenges. The first is spatial grounding. The model perceives objects as pixels, yet
every motion requires a position accurate to about a centimetre, and VLMs judge such distances poorly [15, 22]. The
second is task knowledge: what counts as completion, how deep a plug must be seated, which arm should move first.
Existing approaches place this burden at different levels. Vision-language-action models learn both from demonstrations
collected for each task and robot [9, 12, 43]. Code-as-policies systems expose a fixed set of hand-written primitives,
which the model composes into a program for each instruction [38, 48]. The strongest agent systems instead accumulate
tools, programs or memories for the tasks they encounter, often through many rounds of trial and revision [35, 45, 53, 71].
Such task-specific code is costly to develop and difficult to audit, and it tends to fit the scenes on which it was developed.
Our earlier exploration, HexaShell-TaskTools (HexaShell-Preview), illustrates the problem: an optimizer agent wrote
about 78,000 lines of task tools for RoboDojo over 769 rounds, yet once frozen, these tools passed only 36% of the
development episodes on which they had been built (Sec. 3.4).
In this work we study how far a harness can go when nothing elaborate is written for any individual task. Our approach
rests on an observation about where coding agents fail: most of what they lack is not specific to a task. They need to
know where objects are, to verify a motion before committing to it, and to receive clear feedback when something goes
wrong, and these needs are common to all tasks and robots. The task-specific remainder is small: a success condition
that the instruction leaves implicit, a parameter that only contact reveals, an order of steps. This suggests a division of
labour in which general capabilities are implemented once, as shared and tested code, while task knowledge is conveyed
in a short natural-language skill.
We present HexaShell, a harness built on this division (Fig. 2). A single robot API, agent loop and sandbox serve every
task in every setting; at each turn the model writes one Python cell against the API and reads its output. Perception is
decomposed into segmentation and localization. SAM 3 [14] determines which pixels belong to an object, and geometry
implemented with NumPy and OpenCV determines where those pixels lie in the world, by matching outlines across
calibrated cameras or back-projecting a depth image, so that the VLM never has to estimate a distance. The API is
designed with a language model as its user: motions can be checked before they are executed, results report problems
first, and errors state what to change. Porting to a new simulator or robot requires only an adapter below the API and the
text of the prompt. Task-specific input is limited to an optional skill, about a page of guidance that an analysis agent
drafts from the records of earlier runs and a person reviews.
We evaluate HexaShell on four simulated benchmarks, RoboDojo [20], RoboCasa365 [59], LIBERO-PRO [92] and
RoboTwin 2.0 [19], which together span three simulators, two kinds of arm, fixed and wheeled bases, and cameras
with and without depth, as well as on real dual-arm PiPER-X robots. Without any task-specific input, HexaShell
reaches a success rate of 69.9% on RoboDojo, above every entry of its leaderboard, and in nine episodes out of ten it
writes no vision code of its own. With task skills, it reaches 85.0% on RoboDojo, 85.6% on RoboCasa365, 96.7% on
LIBERO-PRO and 96.8% on RoboTwin 2.0, above the best published result we are aware of on each benchmark (Fig. 1).
The gains from skills stem from a few facts per task. The remaining failures are dominated by grasps that slip, which
originate below the API and lie beyond the reach of any skill.
Our main contributions are as follows.
• Simple and complete general tools.We design a simple and complete set of general tools, shared by all tasks,
through which the model acts by writing Python: goto moves an arm,find segments objects,measure locates
them in 3D and state reports the arms and the remaining steps. Perception separates segmentation by SAM 3
from geometric localization, so that the model receives metric 3D positions with error estimates instead of judging
distances itself, and every motion can be checked in a dry run before it consumes steps. With nothing written
for any task, GPT-6-Astra in HexaShell reaches a success rate of 69.9% on RoboDojo, above every entry of its
leaderboard, whereas the same model in the RoboDojo team’s agent reaches 22.5% (Sec. 3.2).

2 HexaShell
HexaShell separates what is shared from what is specific. A single robot API, agent loop and sandbox, written and
tested once, serve every task in every setting, and their perception and motion tools are general enough that the agent
rarely needs more (Secs. 2.1 and 2.2). Setting-specific input is limited to an adapter below the API and the text of the
prompt (Sec. 2.3); task-specific input is limited to an optional skill, about a page of guidance on the success condition,
the steps that work and a few parameters from earlier runs (Sec. 2.4). Section 3 evaluates the general tools alone, the
transfer of the harness across settings, and the effect of the skills.
Figure 2 gives an overview. The agent loop exchanges messages with the model, whose Python cells run in a sandbox
and call the robot API; perception and motion run behind the API, outside the sandbox. The model reads three texts: a
system prompt, a task card and, when skills are enabled, the task’s skill. Three principles guide the design. First, the
model makes every decision, while the API executes one request at a time and reports the outcome. Second, the agent
observes the scene only through what a real robot also has: camera images (with depth where the benchmark renders it),
camera calibration and the state of the arms. Third, success is judged solely by the benchmark’s own checker.
2.1 Agent loop and robot API
The model interacts with the robot through a minimal tool interface. It executes Python cells in a persistent session,
each returning the printed output, the value of the last expression, any exception and the requested images, and it ends
the episode with a stated reason (App. E.1). The simulation is paused while the model deliberates, so perception and
reasoning are free, and only motion consumes the benchmark’s own step budget.
Inside a cell, the robot is exposed as a single object, robot. Table 1 lists the calls shared by the four simulated
benchmarks, in three groups: motion, perception and state. RoboCasa365 and LIBERO-PRO add a few calls for their
robots (App. E.2), the real robots do not yet provide find, measure or things, and App. F gives the full reference.
Motions are specified as poses of an arm’s grasp point rather than as joint commands. Any motion can first be executed
as a dry run, which reports reachability, path, step cost and proximity to the other arm or to a measured object without
moving the robot, so that the model can test a plan before it spends steps. Motions meant to meet resistance, such as
presses and insertions, are flagged as contact motions and are not stopped early.
The API is designed with a language model as its reader. Each result prints as a short summary with warnings first
(Fig. 3) and remains accessible as a structured object in code. Errors are raised as typed exceptions whose messages
prescribe a remedy. An unreachable pose leaves the robot untouched and comes with a reachable alternative; a stalled
motion or a lost grasp aborts the rest of the cell, so that the model observes the scene again before it continues.
2.2 Grounded perception
Perception addresses two questions: which pixels show an object, and where those pixels lie in the world. HexaShell
answers the first with a learned segmentation model and the second with geometry implemented in NumPy and OpenCV
[11], so that the VLM never has to judge a distance itself. find queries a SAM 3 service, one per machine [14], with a
few words, pixels marked on or off the object, or a box, and returns outlines (masks) with their scores.

2.3 Adapters, sandbox and prompt
The API is identical in every setting; below it, an adapter translates requests into the setting’s own actions and reads its
cameras and arm state. Table 2 lists what lies below the API in each setting, with the lines of Python written for that
setting alone and the length of its system prompt in characters. On the ARX X5 arms of RoboDojo and RoboTwin 2.0,
HexaShell solves inverse kinematics itself; on the Franka Panda of LIBERO-PRO and RoboCasa365, it drives robosuite’s
operational-space controller with a feed-forward planner; and on the real robots, a separate service, URAI [32], plans
and executes every motion (Apps. E.4 and K). The shared core comprises 5,577 lines of vision, 1,255 of robot API, 1,622
of agent loop and 806 of sandbox, plus 2,072 lines of motion for the two ARX X5 settings. The three benchmarks whose
simulators run in a server process also share 4,134 lines (server, protocol and operational-space control). RoboTwin 2.0
has a second version of three prompt parts, for perception with depth.
Cells run in a separate worker process with one persistent Python namespace, and everyrobot call is forwarded to the
host process, which owns the arms, cameras and perception. Landlock and seccomp confine the worker, so that the
simulator, the task code, the skill sources and the network remain out of reach whatever a cell does (App. E.5).

2.4 Task skills
A skill is a Markdown file for one task: about a page of guidance, not a program. Every skill on LIBERO-PRO,
RoboCasa365 and RoboTwin 2.0 has five sections:
•Judging: what counts as done, as earlier runs showed it, with no internal threshold of the checker;
•Flow: the steps that worked, in order, with the calls to use;
•Verified parameters: numbers measured in earlier runs, such as grasp heights, offsets and openings;
•Common failures and fixes: what went wrong and what to do instead;
•Typical step costs: how many steps each phase took, so that the agent can plan its budget.
RoboDojo skills also have a section of final checks and, for the twelve Generalization tasks, one on clutter. Appendix H
shows three skills in full.
Skills are drafted by an analysis agent, which reads the records of earlier runs of a group of related tasks, including every
cell, output and image, and marks the evidence behind each claim; a person reviews every draft. A skill may contain
only what the agent could observe: no positions read from the simulator, no internal names and no checker thresholds, a
constraint enforced by a checking script. The median skill has 39 to 61 lines, depending on the benchmark, and only
three of the 205 skills contain code (App. E.6).
3 Experiments
The experiments address three questions: how far the general tools go without any task-specific input (Sec. 3.2); whether
the harness transfers to other simulators and to real robots when only the adapter and the prompt change (Sec. 3.3);
and what task skills add, measured both against runs without them and against a toolset written for each task (Sec. 3.4).
Section 3.1 describes the benchmarks and the evaluation protocol, and Sec. 3.5 analyses the failures that remain.
3.1 Experimental setup
We evaluate on four simulated benchmarks and on real robots. RoboDojo [20] has 42 tabletop tasks for two ARX X5
arms in Isaac Sim, in five dimensions: Generalization, Precision, Long-Horizon, Memory and Open. Its eight Open
tasks receive no skills, so that they measure the general components alone. On RoboCasa365 [59] we run the 50 target
tasks of its leaderboard, kitchen tasks for a Franka Panda on a wheeled base; on LIBERO-PRO [92], the four LIBERO
suites under its position, object, language and task perturbations; and on RoboTwin 2.0 [ 19], its 50 dual-arm tasks
in randomized scenes with unseen instructions. Prompts, tools and skills are built on development episodes, and the
test episodes differ in their layouts, seeds, kitchens, initial states or instruction templates. Every simulated run uses
GPT-6-Astra, at reasoning effort xhigh for the RoboDojo and RoboCasa365 runs of Tabs. 3 and 4, except RoboDojo’s
6
Open tasks, and high elsewhere. RoboDojo reports a success rate (SR) and a score, both averaged over the tasks of each
dimension and then over the dimensions; the other benchmarks report the share of successful episodes. All results are
our own evaluations on public test episodes, with fewer episodes than the official protocols; App. A gives the protocols
and the choice of compared methods.

3.3 Transfer across simulators and real robots
The same API, loop and sandbox run on three simulators, two kinds of simulated arm on fixed and wheeled bases,
cameras with and without depth, and real robots; only the adapters and the prompt texts differ (Tab. 2). With skills,
HexaShell exceeds the best published result we are aware of on every simulated benchmark (Fig. 1 and Tabs. 3, 4, 8
and 9).
On RoboCasa365 it reaches 59.3% without skills and 85.6% with them, against 64.4% for the best leaderboard entry,
Awomo-0.5I (Tab. 4). The margin is largest on the composite tasks: 85.0% against 58.8% on the seen ones and 80.0%
against 45.2% on the unseen. On the same 1,500 episodes the skills gain 466 and lose 72 (p <0.001), most of them
on tasks at the sink and on appliance doors and buttons. On LIBERO-PRO it reaches 78.3% without skills and 96.7%
with them, and on 54 tasks a paired control raises it from 252 to 531 of 540 episodes; other coding agents report 94.0
to 96.5% on subsets of the benchmark [53, 69, 77], and its leaderboard, which lists only VLAs, tops out at 53%. On
RoboTwin 2.0, in randomized scenes with unseen instructions, it reaches 82.2% without skills on the learning seeds and
96.8% with them on the test, against 81.5% for the top leaderboard entry, GO-3 Nano Preview, and 90.4% for the best
result in a paper.
The same loop, sandbox and API also drive real robots: three dual-arm PiPER-X robots with RGB-D head and wrist
cameras. The 907-line adapter passes each goto to URAI, which plans it, checks it for collisions and executes it; a
refused plan is reported as an unreachable pose, as in simulation. The real robots have no segmentation service yet,
so the model reads pixel coordinates off the images and turns them into points withto_world on the measured depth.
Over the nine tasks of Tab. 5, HexaShell succeeds in 76 of 90 episodes. GPT-6.1-Terra writes the code for all nine and,
in the absence of a checker, GPT-6-Astra judges each episode. The tasks include shuffling, stacking and unstacking
blocks, sorting them by a language instruction, sorting pens from plush toys, putting a papaya in a plate and taking it
out, and PushT. In cover blocks, the agent notes the colours of three blocks, covers them with cups from left to right,
then uncovers them, and succeeds in 10 of 10. Figure 5 shows one successful episode of each task.

3.4 Effect of task skills
Knowledge that a general harness lacks about a task can be supplied either as brief guidance, as in HexaShell, or as an
elaborate task-specific toolset. HexaShell-TaskTools, an earlier version of our agent listed as HexaShell-Preview on the
RoboDojo leaderboard, takes the latter approach. An acting agent (the Codex command-line agent with GPT-6-Astra)
drives the robot through a command line. After each failed episode, an optimizer agent of the same model writes or
repairs the task’s tools, with their tests, and the same layout is tried again. Each task was developed for up to 12 hours
on the first ten layouts of seed 0, the same development layouts that HexaShell used. The 769 optimizer rounds left 327
task commands in about 78,000 lines of Python, which were then frozen. In RoboDojo’s official evaluation, on a hidden
seed with 50 episodes per task, they reach a success rate of 46.9 and a score of 53.2. Table 6 sets this official result
against our two test runs of Tab. 3, overall and per dimension, with the Open tasks counted as in Tab. 3.
The resulting code is large and generalizes poorly. Re-run after freezing, the tools pass only 152 of the 420 development
episodes on which they were built (36%). An audit further found object sizes copied from the scenes into the tools of
seven tasks, a shortcut that a measurement within the episode should replace. HexaShell, by contrast, keeps no tools for
any task. Its 34 RoboDojo skills are plain text, about 2,700 lines in total or about a page per task, each of which a person
can read and verify; only three contain code (App. E.6).
Brief guidance proves more effective than a large toolset. Even without skills, HexaShell outperforms HexaShell-
TaskTools in every dimension. With skills, it reaches a success rate of 85.0 and a score of 88.8, and the gap is largest
precisely where per-task code was expected to help most: Precision and Long-Horizon, 86.3 and 82.9 against 32.0 and
31.5. Although the official evaluation and our test runs use different episodes, the ranking also holds on public episodes:
on 420 episodes of seed 0, with the same layouts outside Generalization, the frozen tools of HexaShell-TaskTools pass
157, HexaShell 284 without skills and 351 with them. Since the two versions also differ in the loop, perception, motion
and prompt, this comparison establishes that general tools with short skills outperform tools written for each task, but
not which change matters most. A paired comparison isolates the skills: of the 1,020 RoboDojo episodes outside Open,
234 succeed only with skills and 37 only without (p <0.001; App. D).

from 14 to 29, while no task loses more than two episodes. These tasks also failed differently from the rest: without a

3.5 Failure analysis
The agent ends most failed episodes itself, mostly because the remaining steps cannot pay for another attempt, and most
failures still earn part of the task’s score (App. I.2). The most frequent cause of failure is an object slipping from the
fingers. With skills, 153 of the 1,020 RoboDojo episodes outside Open contained a slip, and 46% of them succeeded,
against 91% of the others. Skills make slips rarer but do not eliminate them. The Open task store tools in toolbox passes
no episode: as the arm lifts, a long tool gripped near its middle rotates between the fingertips and slides out, and scripted
tests outside the agent never placed the pliers either (App. I.4). These failures originate in the grasps and motions below
the API, which no skill can change; better grasping at that level would benefit every task at once.
4 Related Work
Code generation for robot control.Code as Policies [ 48] has a language model write programs over perception and
control primitives. ProgPrompt [70] and Inner Monologue [37] plan with a language model and feedback from the scene,
and SayCan [5] grounds language in a fixed library of skills. V oxPoser [38] composes value maps for a motion planner,
while ReKep [39] and MOKA [50] let a vision model mark keypoints that code then turns into motion. RoboCodeX
[57] and RoboScript [16] generate manipulation code from images and text, and language models also write reward
functions for policy learning [55, 84]. In these systems the primitives are written by hand, and the model composes
them into a program for each instruction. HexaShell likewise relies on general, hand-written primitives, but it operates
in a closed loop: the model writes one short cell at a time and chooses the next step only after reading the printed results
and the images.
VLM agents as robot policies.A frontier VLM can now serve as the policy itself. Zhanget al. [ 88] evaluate GPT-
6-Astra on RoboDojo through a fixed end-effector harness, with no learned policy in the loop. Show-Harness [ 21],
Agent as Policy [40], VIA [36] and World Action Agent [89] drive robots through a VLM agent and a fixed interface.
Robo-Harness K1 adds perception tools for such agents [ 47], and RoboDawn reports GPT-6-Astra on RoboDojo
zero-shot and one-shot [33]. Harness VLA [90] lets a memory-guided agent steer a frozen VLA through manipulation
primitives, and OmniBrain-0 [81] is a single agentic model for embodied tasks. CaP-X [28] and LIBERO-Agent [24]
benchmark coding agents and general agents on manipulation, RLE-Bench [54] tests coding agents as robot learning
engineers, and EmbodiedLab [30] tests whether agents act on a scene to find out what a task requires. The agent track of
the RoboDojo leaderboard lists Q0-Preview [64], PyRUA-Lean [69] and EmbodiedEvo [45] as standalone agents, and
GO-3 Nano Preview [4], WorldScape-R2SI [56] and PhysicalRSI [35] as agents that direct a learned model (App. A.2).
HexaShell belongs to this family and differs mainly in its interface, whose calls return measured 3D positions with error
estimates, check a pose before it consumes steps, and report problems first, together with what to change.
Self-improving coding agents.Coding agents read a repository, run its tests and fix the code [ 18, 41, 78, 82], and
Reflexion [68] keeps verbal lessons from failed attempts. V oyager [73] grows a library of code skills while playing
Minecraft. Toolformer [67] learns when to call tools, LATM [13] and CRAFT [85] have language models write and
retrieve tools, and self-improving systems modify their own programs and retain the changes that raise a score [52, 60, 86].
In robotics, recent harnesses let coding agents program, test and refine robot skills [17, 25, 26, 53, 72, 74, 80, 87], some
starting from a few human demonstrations [42, 51]. URAI pairs a programming agent that writes motion tools with
an execution agent that calls them [32]. EmbodiedEvo turns physical feedback into code skills and diagnostic lessons
[45], MEMENTO evolves code policies with a memory of past programs [71], and Gaoet al. [ 31] treat tools, traces and
memory as code that a physical coding agent revises. In most of these systems, what is retained for a task is code, as in
HexaShell-TaskTools, an earlier version of our agent that wrote and repaired tools for each task (Sec. 3.4). In HexaShell
the code is general and fixed, and what is retained for a task is only a short, reviewed skill in natural language. In this
respect it is closer to Reflexion’s verbal lessons than to a skill library.
Visual grounding for manipulation.SAM [ 44], SAM 2 [66] and SAM 3 [14] segment objects from points and boxes,
and SAM 3 also from short phrases. VLMs, by contrast, judge positions and distances in an image poorly [ 29, 65];
SpatialVLM [15] and SpatialRGPT [22] train them on spatial data to close this gap. Monocular depth networks predict
depth from a single image [10, 75, 76, 83]. Multiple-view geometry recovers a point from two calibrated views [34],
plane sweep tests candidate depths by comparing views [23], and both are standard in OpenCV [11]. Active perception
12
moves the sensor to obtain a better view [6, 8]. In HexaShell the VLM never estimates a distance itself: it names an
object or points at pixels, SAM 3 returns the outline, and calibrated geometry or rendered depth yields the position with
an error estimate. The model decides when a wrist camera should add a view, a simple form of active perception.
Learned policies and benchmarks.Vision-language-action models [ 9, 12, 43, 61–63, 94] learn manipulation from
demonstrations, some collected with low-cost hardware [ 91]. They are evaluated on suites such as LIBERO [ 49],
RoboCasa [58, 59], RoboTwin 2.0 [19] and SIMPLER [46], and in autonomous real-world evaluation [93]. LIBERO-
PRO [92] and LIBERO-Plus [27] perturb LIBERO’s objects, positions, instructions and scenes, so that a policy cannot
succeed by memorizing the training layouts. RoboDojo [ 20] fixes a step budget per task, tests on several seeds and
pairs clean layouts with cluttered ones. Most leaderboard entries on these benchmarks are learned policies, so our
comparisons set an agent that uses no demonstrations against policies trained on many.
5 Limitations
Our results come from our own evaluations on public test episodes, with fewer episodes than the official protocols. A
skill requires runs of its task, so a new task starts at the level of the general components, and we have not measured how
few runs suffice. We have not yet quantified the contribution of SAM 3 and the geometry by switching them off. Slips
of held objects remain the most common failure, and the real robots run without SAM 3, with few episodes so far.
6 Conclusion
We presented HexaShell, a harness in which a VLM controls robots by writing one Python cell per turn against a small
robot API. Task-agnostic tools carry the agent most of the way: SAM 3 for segmentation and NumPy and OpenCV
geometry for localization, shared unchanged by four simulated benchmarks. The real robots use the same loop, sandbox
and geometry but have no SAM 3 yet, so there the model picks the pixels itself. About a page of guidance per task,
distilled from earlier runs, supplies what such tools cannot know, namely the success condition, parameters that only
contact reveals and the order of steps, and in our own evaluations it lifts the agent above the best published result we are
aware of on all four benchmarks.
Most remaining failures are slips of held objects and final placements that must be exact. Better grasps and motions
below the API would benefit every task at once. They are the focus of our next steps, together with the official evaluations,
more real-robot episodes and an ablation without SAM 3.

A.1 Benchmarks and runs
Table 7 lists, for each benchmark, the development and test episodes, the agent’s limits per episode (App. E.1) and
the official test protocol, which we did not run. On RoboCasa365 the reply limit is 100 on composite tasks and 40 on
atomic ones, and LIBERO-PRO’s step limits leave out its ten settling steps. The official evaluation of RoboTwin 2.0
covers clean as well as randomized scenes, and that of RoboCasa365 uses its pretraining kitchens. RoboDojo [20] has
42 tabletop tasks for two ARX X5 arms in Isaac Sim, in five dimensions: Generalization (12 tasks, half of whose test
episodes add clutter), Precision (8), Long-Horizon (8), Memory (6) and Open (8). RoboCasa365 [59] has kitchen tasks
for a Franka Panda on a wheeled base, and we run the 50 target tasks of its leaderboard. LIBERO-PRO [92] perturbs the
four LIBERO suites [49]: objects are moved (position), changed in appearance (object), the instruction is reworded
(language), or a different task is asked in the same scene (task). We run these four perturbations. The fifth, which
changes the environment, is not in the release and has to be generated; we have not run it. RoboTwin 2.0 [19] has 50
tasks for two ARX X5 arms in SAPIEN. We run its clean-to-randomized setting (“hard” on its leaderboard): randomized
scenes with clutter, textures, lighting and table height, and instructions from the templates kept for testing (unseen). The
test seeds are chosen as in the official evaluation, the first seeds from 100000 whose scenes the benchmark’s expert
solves.
Every simulated run uses GPT-6-Astra through an OpenAI-compatible gateway (the real robots’ models are given in
App. K). The two runs of Tab. 3 and the two of Tab. 4 use reasoning effort xhigh, with at most 32,000 output tokens per
reply on RoboDojo and 8,192 on RoboCasa365. All other runs use effort high with at most 8,192: the LIBERO-PRO
and RoboTwin 2.0 results, the harness comparisons of Tab. 14, and the RoboDojo Open tasks, whose one run both rows
of Tab. 3 share. In that run, store tools in toolbox, which had passed none of its 30 episodes in an earlier run, was not run
again and counts as 0. Two runs kept a larger picture window than that of App. E.1: that Open run (90 and 60 pictures
and 10 MB instead of 20, 14 and 8 MB) and the RoboCasa365 run without skills (50 and 30 pictures).
Prompts, tools and skills were built on the development episodes of Tab. 7, not on the test episodes. On RoboDojo these
were five rounds on seed 0 and layouts 0–9 (R0–R4); on RoboCasa365, learning seeds 0–9 and validation seeds 10–19 of
the pretrain50 split; on LIBERO-PRO, learning states 0–9 and validation states 10–19; and on RoboTwin 2.0, ten learning
and ten validation seeds per task below 100000. Between R0 and R1, which added the first skills and a new motion
planner, successes on the 34 tasks outside Open rose from 173 to 251 of 340, and R4 solved 330 of 422 episodes of all
42 tasks. The test episodes differ from the development ones in their layouts and seeds (RoboDojo), seeds and kitchens
(RoboCasa365), initial states (LIBERO-PRO), and seeds and instruction templates (RoboTwin 2.0). RoboDojo’s layouts
10–19 are public, while its official evaluation uses layouts that are not. HexaShell has been submitted to RoboDojo’s
official evaluation.

A.2 Metrics and comparisons
RoboDojo reports a score, the task progress that each task’s score table defines, and a success rate (SR). As RoboDojo
computes them, both are averaged first over the tasks of each dimension and then over the five dimensions. The eight
Open tasks therefore weigh as much as the twelve Generalization tasks, and the SR differs from the share of successful
episodes. Without skills it is 69.92 for 857 of 1,260 episodes (68.0%), and with skills 85.00 for 1,054 of 1,260 (83.7%).
We report the mean and standard deviation over the three seeds. The other benchmarks report the share of successful
episodes, and RoboCasa365’s overall number is the mean over its 50 tasks. A paired comparison runs the same episodes
twice, and we test it with an exact two-sided sign test on the episodes that succeeded in only one of the two runs.
For each benchmark we list the leaderboard entries on the date given in its table and results reported in papers; we ran
no other method. HexaShell-TaskTools’s results come from RoboDojo’s official evaluation and from our retests of its
frozen tools (Sec. 3.4). Leaderboard entries follow the official protocol and papers use their own episodes, often on a
subset of tasks or perturbations, so neither comparison with our evaluations is exact. Figure 1 draws the top three other
entries of each leaderboard in its own ranking: on RoboDojo [2], Q0-Preview, GO-3 Nano Preview and PyRUA-Lean, by
average score on 30 October 2026; on RoboCasa365 [1], Awomo-0.5I, minionx and Axiom-0, leaving out Awomo-0.5V ,
a second model of the Awomo team; and on RoboTwin 2.0 [3], GO-3 Nano Preview, PrismW AM* and PICA-W AM, by
the mean of the easy and hard settings, drawn in the hard setting that we ran. The LIBERO-PRO leaderboard lists only
VLAs, the best at 53% over five perturbations, so there the figure draws the three highest results in papers, each on its
own cells: HarnessPAI, 96.5% on the position and task perturbations of three suites [77]; ASPIRE with GPT-6-Astra,
96.0% on the same perturbations of all four suites (our mean of its eight per-cell results; 98.8% with Claude Opus 5.5)
[53]; and PyRUA-Lean with GPT-6-Astra, 94.0% on 40 tasks with five seeds each [69].
RoboDojo’s leaderboard [2] marks each entry of its agent track as an agent alone or as an agent that directs a learned
model. Q0-Preview [64], PyRUA-Lean [69], EmbodiedEvo [45], the RoboDojo team’s GPT-6-Astra agent [88] and
HexaShell-Preview, our HexaShell-TaskTools (Sec. 3.4), are agents alone. GO-3 Nano Preview [4] and WorldScape-R2SI
[56] direct a world action model, and PhysicalRSI [35] a VLA.

C.8 What the cases show
Since the two runs of each episode differ only in the skill, the success with it shows that the agent could perceive and
handle the objects of that episode. What it lacked without the skill was a fact about the task, which the skill supplied in a
few lines. The facts are of the three kinds named in Sec. 3.4. Three are success conditions that the card leaves open:
which tile to place and where it stands (make kong), which end of each pen goes up (fill pen holder) and when a moved
box still counts as aligned (pack objects into box). One is a parameter that only contact reveals: a turn that pushes the
nut down, with the measured heights that tell a seated nut from one on the tip (fasten screws). Two concern the ordering
of steps: each pillar level is built from one pillar of each side (build tower), and the arm and pitch of the whole carry are
settled by dry runs before the first slice is grasped (make toast). In five of the episodes, the agent without the skill spent
its remaining steps on a repair that the skill rules out: straightening the box, turning the nut back and forth, moving the
discard, taking apart the top of a tower whose lower pair could not be credited, and recovering a fallen slice while a third
one took its slot. Each of these facts came from development runs in which an attempt succeeded or failed for a reason
that the card does not state. The skills leave other failures in place. With the skill, fill pen holder still fails 14 times, each

and the one failure of build tower stopped at a finished tower for a reason the record does not show. The make-toast

30◦ and lost one, whereas the agent without it handed the slices between the arms, which the skill advises against, and

E Implementation details
E.1 Agent loop
The model has two tools: python(code) runs one cell, andfinish(status, summary)ends the episode. A reply may
hold several cells, which run in order. The status of finish gives the reason: no_budget when the steps left cannot
cover another attempt, stuck when there is no way forward, and keep_partial when another attempt would put a
partial result at risk. The episode ends when the benchmark ends it, when the model calls finish, or at a limit on replies
and time: 100 replies and 90 minutes on RoboDojo, and 40 replies (100 for RoboCasa365’s composite tasks) and two
hours on the other benchmarks. The benchmark ends an episode on success, which it checks after every action, or when
the step budget is spent. The scene is then judged as it stands. A step is one simulator action (0.04 s of simulated time on
RoboDojo).
Pictures are sent as JPEG images. The model’s gateway accepts 8 to 10 MB per request, so only a window of pictures
stays in the conversation. The start pictures on the task card are always kept. When the others pass 20 pictures or 8 MB,
the oldest are replaced by a short placeholder until 14 remain. Two runs used a larger window (App. A). Dropping
several pictures at once keeps the cached start of the conversation valid for longer. The loop also supports Claude models
and open models served with vLLM.
E.2 Robot API conventions
Positions are in metres in the benchmark’s world frame and angles in degrees. Pixels are (column, row) from the top-left
corner. Pitch 0 points the hand level and 90 points it straight down. Yaw turns the hand about the vertical and roll about
its own axis. look attaches the current pictures to the cell’s result, optionally with a pixel grid, marked points, outlines,
or an enlarged crop. The labels on a crop stay in full-picture pixels, so a pixel read off any picture can be passed to the
other calls as it is.
A benchmark adds calls only where its robot can do more. On RoboCasa365 the base drives (drive), and doors and lids
turn about their hinges (arc,push_arc). A helper there picks a round dish by its rim (rim_pick). LIBERO-PRO also
hasarc. Both benchmarks also hand the cell the raw depth picture (depth).
E.3 Perception
The design grew out of the task tools of HexaShell-TaskTools (Sec. 3.4), which triangulated objects between calibrated
RGB cameras inside each task’s own code. Here one service and one set of geometry serve every task, with depth where
a benchmark renders it.
One SAM 3 service [14] runs on each machine and serves every episode there. A picture is uploaded once and then
named by its hash. Words find by appearance only.Leftorseconddo not pick an instance, so the model chooses among
the masks by their centroids or points at the one it means.
RoboDojo has no depth camera, someasure works from outlines alone. A mask in one picture fixes a cone: the rays
through its pixels, down to the table. To find the same object in another camera, the service is asked again, with the
33
same words, or with clicks along the middle ray of the first outline at several heights above the table. Each candidate is
scored by how well the two cones contain each other’s outline, and colour breaks near ties. The object then lies in the
space that every camera able to see a point shows inside its outline, a visual hull that is probed along the pixels’ rays.
Its top is the lowest height that still explains almost all outline pixels. Its footprint comes from the surface points each
camera sees below the top. A rotated rectangle fitted to the footprint (cv2.minAreaRect) gives the object’s size and
grip_yaw, the yaw that closes down-pointing fingers across its narrow side. Pixels that show the robot’s own arm do
not count against an outline. They are found by drawing the arm’s meshes at the current joint readings. With one camera
the height cannot be measured. The object is then taken to rest on its support, and the result says so and gives a wrist
pose that would add a view.
to_world(cam, (x, y))turns a pixel into a world point. A pixel fixes a ray, and the depth along it comes from one of
three sources. The first is a horizontal plane at a height the model gives (a rim, a slot, the table). The second is the same
point picked in a second picture: the two rays are intersected, and a gap of more than about 5 mm between them reveals
a mismatch [34]. The third is the surface under the pixel. This is the table, a measured object, or a level patch that is
matched between cameras by zero-mean normalized cross-correlation over candidate heights, a plane sweep [23]. Every
result reports how far one pixel of picking error moves the point, and it warns when the pixel shows the robot’s own arm.
LIBERO-PRO and RoboCasa365 render a depth picture with every camera. There the same calls back-project a mask’s
pixels through the depth picture and merge the points of all cameras that see the object. An oriented box on the floor
plan gives the centre, size and grasp yaw, and the lowest and highest points give the height. Only the visible surface is
measured, so when the cameras see an object from one side only, its centre leans toward them by up to half its depth.
For pinch grasps, a circle fitted to the depth points around a round dish gives the outer edge of its rim. RoboTwin 2.0
renders depth as well, but in all our RoboTwin runs perception used only the colour pictures and the camera models, as
on RoboDojo. On these three benchmarks the robot’s own pixels come from the renderer’s segmentation of the robot’s
parts, not from its meshes.
Measured objects keep their id for the whole episode. Measuring an object again looks for it where it was last seen, or
where the gripper has taken it, and falls back on its earlier height when only one camera sees it now. The RoboDojo
prompt gives the model the errors to expect. From the start pictures, low box-like objects (blocks, tiles, small flat things)
usually come out within a few millimetres. Round, hollow or tall objects (balls, bowls, cups, bottles) are often 1–3 cm
off, and too high or too large rather than too low. A wrist camera held about 25 cm above the object, together with the
head camera, brings the error to 1–2 mm. Pixels read from an enlarged crop are about twice as precise as pixels read
from the whole picture.
E.4 Motion
On RoboDojo, HexaShell runs as a policy inside the benchmark’s own evaluation client, which asks for one action at a
time. While the model thinks, the policy answers “wait”, so the simulation stands still and no step is used. On the other
three benchmarks the simulator runs in a server process with its own Python environment and talks to HexaShell over a
socket.
On RoboDojo and RoboTwin 2.0 the arms are ARX X5 arms and take joint targets. HexaShell solves inverse kinematics
itself, with Levenberg–Marquardt steps on the 6-D pose error of the grasp point from several starting configurations.
Of the solutions that keep the arm out of the table, it takes the one with the least joint travel. A straight path is solved
waypoint by waypoint, and a swing is checked for table clearance along the way. Motions follow a trapezoid-like
speed profile, so long moves across the table take fewer steps while the last centimetres of a descent stay slow. A short
description of the rig (where the arms stand, where the table is, how the gripper reading relates to the fingers) lets the
same driver serve both benchmarks.
On LIBERO-PRO and RoboCasa365 a Franka Panda runs under robosuite’s operational-space controller in delta mode.
That controller lags a moving goal by about 0.16 s and does not compensate a held load. The adapter therefore plans a
straight line on one speed profile and aims each step past the plan, by feeding forward the plan’s velocity and acceleration
and slowly integrating what is left at rest. The same planner serves both benchmarks. On RoboCasa365 the arm also
rides on a wheeled base.
34
E.5 Sandbox
The model’s cells run in a separate worker process with one persistent Python namespace, so variables and functions
survive between cells. Every robot call is forwarded to the host process, which owns the arms, cameras and perception,
and waits for the answer. After the worker has imported what it needs, it confines itself in three layers. Landlock limits
file access to a few read-only trees (the Python installation, the HexaShell package and system libraries) and the worker’s
own workspace, and it blocks every TCP connection. Seccomp forbids network sockets where Landlock cannot block
them, new programs and processes, and signals to or tracing of other processes. At the Python level, imports are limited
to a list of modules (numpy, math, cv2, json and similar) andopen to the workspace. These last limits give clear error
messages but are not the boundary. A cell may use a limited amount of CPU time; waiting for robot calls does not count.
The simulator, the task code, the layouts, the skills’ sources and the network are therefore out of reach whatever a cell
does.
E.6 Writing the skills
Skills are written from the records of earlier runs and, where HexaShell-TaskTools had tools for a task, from what those
tools had shown. Each claim carries its evidence. On the three newer benchmarks this is the number of episodes it was
seen in, such as “(7 eps)”, or a mark for a probe, a scripted test, a HexaShell-TaskTools tool, or “untested”. RoboDojo
skills name the development round and layouts instead, such as “R0 8/8” or “(l0)”. A checking script enforces the rules
of Sec. 2.4 together with the format. On the three newer benchmarks a skill has at most 45 lines of 100 characters. On
RoboTwin 2.0 the skills use only the instruction wording of the learning runs, never the unseen wording of the test. The
RoboDojo skills went through four versions during the development rounds on layouts 0–9 of seed 0. The skills cite
only learning and validation episodes.

K Real-robot details
The URAI adapter connects the API to two PiPER-X arms with a head camera and two wrist cameras, all RGB-D.
URAI [32], a separate service, plans and executes every motion: inverse kinematics, collision checking, time scaling and
execution. For eachgoto the adapter sends URAI the target, asks for a planning-only preview of the whole trajectory,
and executes it if the plan is accepted. With path="auto" it tries a straight line first. Otherwise it accepts a joint-space
path only if the path stays within 3 cm of the line and no more than 1 cm below its end points. A refused plan raises
NotExecuted as in simulation, and a grasp that closes on nothing raises Dropped. Steps are counted as executed time
in units of 0.04 s, so a step budget buys about as much robot time as on RoboDojo.
The adapter has no segmentation service at present, sofind,measure andthings are absent. The model reads pixels
off the pictures, with a grid or an enlarged crop, andto_world turns each pixel into a point. It uses the measured depth
first, then a plane at a height the model gives, then a second view. The model checks a point by projecting it back with
to_pixel and marking it in a new picture. The robot’s own pixels come from URAI’s collision capsules, projected into
each picture and compared with the measured depth.
The real-robot prompt keeps the six parts of Sec. 2.3 in 11,110 characters of English. A real robot has no checker, so
finish has one more status,done. The model’s report is stored with the episode. The adapter has 907 lines. The loop,
the sandbox and the geometry of to_world above it are the code that runs the simulated benchmarks. The adapter’s 29
end-to-end tests pass against URAI’s kinematic simulator.
The block tasks run as a loop in which each task leaves the scene for the next, and for the pens and plush toys a person
resets the scene by hand before each episode. The block tasks also have more episodes on record than Tab. 5 shows.

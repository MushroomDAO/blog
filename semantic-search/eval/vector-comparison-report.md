## 核心发现

### 1. 跨语言检索缺口被向量检索直接补上（本实验最重要的结果）

`semantic-search/eval/baseline-results.md` 记录的最大缺口——中文短语"脑仿真 大脑连接组"
关键词检索 0 结果，但博客里确实有对应的英文标题文章——**向量检索直接在第一位命中**
（`brain-connectome-data-size-fly-human-mouse`，相似度 0.526）。这是本次实验单条最有说服力
的证据：纯词法检索无法跨语言桥接，向量检索可以。

### 2. 同主题中英文查询下，向量结果高度一致；关键词结果差异悬殊

- "递归自我改进 RSI"（中文） vs "recursive self improvement"（英文）：
  - 关键词：1 条 vs 9 条，结果集合几乎不重叠
  - 向量：两者 top5 **几乎完全相同**（同样是 awesome-rsi / OpenRSI / AgentOptimizer-ProRL /
    Prime Agent / realtime-rl-agent），相似度分数也接近
- "我想本地部署一个 AI 视频编辑工具"（中文自然语言） vs "open source video editing agent"（英文）：
  - 关键词：0/1 相关 vs 5/5 相关，天壤之别
  - 向量：1/5 精确 vs 2/5 精确，同样不对称，但幅度小得多——而且向量在两条查询里都至少找到了
    真正相关的文章（`video-use`），关键词在中文版本上则完全找不到

这正是 `semantic-search/PLAN.md` 里预期向量检索该解决的问题：多语言 embedding 模型不区分
查询语言，直接在语义空间里检索，天然消除了关键词检索的语言壁垒。

### 3. 但向量检索在精确技术名词/多词组合查询上出现了两次明显退步

- **WebGPU**：关键词命中 3/5 相关（three-vrm/Astral3D/Online3DViewer），向量检索 0/5 相关，
  飘向"GPU/硬件"这个更宽泛的语义邻域，丢失了"WebGPU"这个精确技术名词的区分度。
- **terminal AI coding tool**：关键词 5/5 精确命中，向量检索只有 2/5 真正相关，混入了
  `FireRed-OpenStoryline`（视频剪辑，无关）、`FinceptTerminal`（Bloomberg 终端平替，与
  "AI coding tool" 无关）这类因为"terminal"/"tool"字面语义邻近但主题不符的假阳性。

这与 `CODEX_REVIEW.md` 里的预警完全吻合："向量召回对精确技术名词、版本号、错误码、函数名
通常不如词法检索"——本次实验实际观测到了这个现象，不是纸上谈兵。

### 4. 负样本上，向量检索比关键词检索更容易给出"看似合理但边缘"的匹配

- "菜谱 家常菜做法" 向量检索命中了 `epicure-food-ingredient-embedding-geometry`——这篇文章
  确实是关于"把菜谱压进向量空间"的技术文章，语义上与"菜谱"相关，但用户如果是想找"家常菜做法"，
  这条推荐会造成误导。关键词检索在这条上是干净的 0 结果。
- "育儿经验分享" 向量检索命中了一篇儿童课程知识图谱文章，同样是语义邻近但不是真正想要的内容。

**这说明纯向量检索如果没有相关性阈值/无结果判定，会比关键词检索更容易"自信地给出一个不太对的
推荐"**——这正是 `PLAN.md` 架构里强调"设置最低相关性阈值、不能把 chunk/文章 top-K 直接当
可信结果返回"的原因，本次实验提供了具体例证。

## 汇总指标（与基线同口径，20 条非负样本查询；按 Codex 独立复核后收紧的标准重新统计）

| 指标 | 关键词基线 | 纯向量 |
|---|---:|---:|
| Success@5（仅精确/强相关） | 12/20 = 60% | 10/20 = 50% |
| Success@5（含主题相关的弱匹配） | 16/20 = 80% | 18/20 = 90% |
| 精确技术名词类查询明显退步数 | — | 2 条（WebGPU、terminal AI coding tool） |
| 负样本给出"主题相关但意图不符"的误导性匹配数 | 0/4 | 2/4（菜谱、育儿） |

**注意这次改动了什么**：第一版报告按较宽松的标准算出向量 80% strict，看起来单方面碾压关键词的
60%。收紧标准、要求"精确匹配查询意图"而不是"主题沾边就算"之后，向量的 strict 分数反而降到了
50%，比关键词基线还低。**这不代表向量检索没用**——弱匹配口径下向量仍是 90% vs 80%，而且它赢的
地方（跨语言、EN/ZH 一致性、松散概念性提问）是关键词结构性做不到的，输的地方（精确技术名词）
关键词本来就强、可以继续靠关键词兜底。真正的结论是：**向量和关键词各自有明确的优势场景，谁都
不能单独覆盖全部查询类型**，这比"向量整体更好"这种简化结论更接近实情，也更直接指向"必须做
融合"而不是"选一个用"。

## 对照 PLAN.md 的 Go/No-Go 门槛

> 只有满足以下任一条件，Phase 1 才值得做：
> - 跨语言查询的 Recall@5 相对本基线有明显提升 → **满足，且是决定性证据**（§核心发现 1、2；
>   #11 是从 0 结果到精确命中，#15/#16 与 #7/#20 的 EN-ZH 一致性提升也很清楚）
> - 整体质量不低于关键词基线，且自然语言/宽泛问题的召回有可感知改善 → **部分满足**：strict
>   口径下向量（50%）其实比关键词（60%）低，但弱匹配口径下向量（90%）高于关键词（80%），
>   且 #10/#15/#17 这几条自然语言/宽泛查询向量确实有实打实的改善（不只是"沾边变多"，是真的
>   命中了关键词完全找不到的文章）
> - 精确技术名词类查询没有因为引入向量检索而明显变差 → **不满足**（WebGPU、terminal AI
>   coding tool 两条查询用纯向量检索确实变差了，且这次是按严格标准复核过的，不是判断松散
>   导致的假象）

## 建议

**明确的结论只有一条：纯向量单独替代关键词不成立**——WebGPU、terminal AI coding tool 两条
精确技术名词查询用纯向量会退步，负样本也比关键词更容易给出误导性匹配。这直接验证了
`PLAN.md` Phase 1 architecture 一开始就坚持的设计：**关键词 + 向量融合、按 article_id 聚合、
带相关性阈值**，不是"选一个用"的问题。

**"值不值得投入 Phase 1 的工程量"这一条相对没那么斩钉截铁**：strict 口径下向量并不比关键词
基线好（50% vs 60%），它的价值集中体现在几个具体场景——跨语言检索（#11，决定性）、EN/ZH
查询结果一致性（#15/16、#7/20）、松散概念性提问（#10）。这几个场景是否值得为它单独建一套
Vectorize + Workers AI 的在线服务，还是可以先用更轻量的方式部分覆盖（比如给 Pagefind 的
中文分词/同义词做优化，或者只对负样本明显、关键词完全查不到结果时才 fallback 到向量），
是 T1.2.2 需要权衡的产品判断，本报告不替用户做这个决定。

评测样本只有 24 条查询、判断只有一人（过程中经 Codex 独立复核发现并修正了 2 处评分过松），
如果决定 go，建议把这批查询留作 Phase 1 上线前的回归测试集，而不是仅凭这一次性实验的结论
就直接全量上线。

以上是数据和分析，最终 go/no-go 由 T1.2.2 人工裁定。
